# Протокол веб-клиента MAX (web.max.ru)

Неофициальный, получен наблюдением за трафиком `web.max.ru` (ноябрь 2026, `appVersion 26.11.3`)
скриптом [tools/max-traffic-recorder.js](../tools/max-traffic-recorder.js) и сверен с исходниками PyMax.
Может измениться без предупреждения.

## Транспорт

`wss://api.oneme.ru/websocket`, заголовок `Origin: https://web.max.ru`. Одно постоянное соединение,
кадры **бинарные**.

## Кадр

Заголовок 10 байт, big-endian, затем тело:

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | `ver` = 10 |
| 1 | 1 | `cmd`: 0 запрос или уведомление сервера, 1 ответ, 3 ошибка |
| 2 | 2 | `requestId` |
| 4 | 2 | `opcode` |
| 6 | 1 | `flags`: 0 без сжатия, 1..254 LZ4, 255 Zstd (не встречалось) |
| 7 | 3 | длина тела |

Тело — MessagePack. При `flags` 1..254 это **LZ4 block** без заголовка с размером (проверено на
сотнях кадров). Клиент отправляет короткие кадры без сжатия, сервер принимает.
Пустое тело (длина 0) — например, ответ на пинг.

### 64-битные числа

ID и времена в кадрах сервера (веб-клиент в своих запросах делает так же) кодируются как **msgpack ext
type 1**. Данные ext — это обычное msgpack-целое: fixint (1 байт), `int32` `0xd2` (5 байт),
`uint64` `0xcf` или `int64` `0xd3` (9 байт). Так же закодированы ключи некоторых map
(`participants`, `presence`). Обычные небольшие числа (`requestId`, счётчики, `presenceSync = -1`)
идут как обычные msgpack-числа.

**Наш клиент шлёт все числа обычными целыми, без ext** (так проще). Это не проверено на отправке сообщения:
веб-клиент в одних запросах шлёт `chatId` как ext, а в подтверждении уведомления как обычное число, то есть
сервер, судя по всему, разбирает число по значению. Читать ext-числа из ответов клиент по-прежнему умеет.

## Старт сессии

| # | opcode | Направление | Тело |
|---|---|---|---|
| 1 | 6 | запрос | `deviceId` (UUID из `__oneme_device_id`), `userAgent {deviceType: "WEB", pushDeviceType: "WEBPUSH", locale, deviceLocale, osVersion, deviceName, headerUserAgent, isPwa: false, appVersion, screen, timezone}` |
| 2 | 19 | запрос | `token` (`__oneme_auth`, около 700 символов), `chatsCount`, `lastLogin`, `interactive: true`, `chatsSync`, `contactsSync`, `presenceSync: -1`, `draftsSync`, `configHash` |
| 3 | 19 | ответ | `profile.contact.id`, `chats[]` (`id`, `type` DIALOG/CHAT/CHANNEL, `lastMessage`, ...), `contacts`, `presence`, `config`, `time` |

Затем веб-клиент сам запрашивает контакты (32), папки (272), баннеры (302), стикеры (27),
присутствие (35), сторис (208) и шлёт пинг. Для приёма сообщений это не нужно.

Пинг: `opcode 1`, тело `{interactive: true}`, примерно раз в 30 секунд; ответ пустой.

## Новое сообщение

Сервер присылает `cmd 0`, `opcode 128`:

```
{ chatId, message: { id, time, type: "USER", sender, text, attaches: [] },
  prevMessageId, ttl: false, unread: 1, mark }
```

Клиент **подтверждает** каждое уведомление кадром с тем же `requestId`:
`cmd 1`, `opcode 128`, тело `{chatId: <число>, messageId: <число>}`.
Правки и удаления приходят в том же `opcode 128` с `message.status` (`EDITED`, `REMOVED`); у нового сообщения поля нет. В коде это `MaxMessageStatus` (`New`, `Edited`, `Removed`, а незнакомое значение читается как `Unknown`).

В уведомлении нет типа и названия чата, а `sender` — только числовой ID. Чата может не быть
в снимке при входе, тогда тип и название нужно запрашивать отдельно (`CHAT_INFO` 48,
`CONTACT_INFO` 32). Формат этих запросов пока не снимался.

## История чата

`opcode 49`: `{chatId, from: <время, мс>, forward: 0, backward: 30, getMessages: true}`, ответ
`{messages: [...]}`. Сообщения в том же формате, что и в уведомлении, вложения в `attaches`.
Через историю можно увидеть типы вложений, не дожидаясь новых сообщений.

**Запрос «вперёд»** (проверено на живой сессии): `{chatId, from: <время, мс>, forward: N, backward: 0,
getMessages: true}` возвращает сообщения, начиная с `from` **включительно**, по возрастанию ID.
ID в чате растут вместе со временем и не повторяются. Размер страницы сервером может быть
ограничен, поэтому листать нужно повторными запросами с времени последнего полученного сообщения.

## Догрузка пропущенного (как это делает клиент)

После входа MAX присылает снимок: `chats[]`, у каждого чата `lastMessage` (`id`, `time`, ...).

1. Клиент хранит **в памяти** для каждого чата ID и время последнего доставленного сообщения
   (в коде `_lastDeliveredByChat`). На диск ничего не пишется.
2. Если `lastMessage.id` чата больше ID последнего доставленного сообщения, запрашивается история `forward`
   с времени этого сообщения, пока на странице появляется что-то новее уже виденного (удалённые сообщения
   тоже считаются, иначе страница из одних удалённых остановила бы листание).
3. Новое сообщение доставляется только если его ID больше ID последнего доставленного в этом чате: так нет
   дублей, как бы оно ни пришло (живое уведомление, история, повтор после обрыва). Правки и удаления
   проходят всегда.
4. Живые уведомления на время загрузки придерживаются и публикуются после неё, чтобы порядок не
   нарушился, а «последнее доставленное» не перескочило через ещё не загруженные сообщения.
5. Первый вход после запуска приложения: выдаются `InitialMessageCount` (по умолчанию 20) последних
   сообщений из всех чатов вместе. Для этого чаты берутся от самого свежего (по `lastMessage` из снимка), у
   каждого запрашивается история назад (`from` = сейчас, `backward` = N), и набор обрезается до N самых
   свежих; когда следующий чат уже старше самого старого из набранных, перебор останавливается. У остальных
   чатов «последнее доставленное» ставится на их последнее сообщение. Чат, которого ещё нет среди
   доставленных, загружается с момента запуска приложения.
   **Это состояние не переживает перезапуск:** после каждого запуска последние N сообщений приходят снова, а
   сообщения, пришедшие за время простоя и не попавшие в последние N, теряются.
6. Снимок содержит только недавние чаты (`chatsCount`), поэтому если за время простоя активными стали
   больше 40 чатов, самые старые из них не догрузятся.

## Отправка сообщения

`opcode 64`, запрос:

```
{ chatId, message: { text, cid, elements: [], attaches: [] }, notify: true }
```

`cid` — id сообщения на стороне клиента (число, судя по виду, время в мс). Ответ:
`{chatId, message: {id, time, type: "USER", sender, cid, text, attaches}, unread, mark}`.
Перед отправкой веб-клиент шлёт `opcode 65` (набор текста), после — `opcode 177` (сброс черновика).

## Фото

Отправка (реализована в `MaxClient.SendPhotosAsync`):

1. `opcode 80`, `{count: 1}`, ответ `{url}`: адрес вида `https://iu.oneme.ru/uploadImage?r=<токен>`.
2. HTTP `POST` на этот адрес сразу после ответа 87, тело — сырые байты файла (не multipart). Заголовки
   запроса, сняты с настоящей загрузки веб-клиента:
   - `Content-Type`: тип файла, который определил браузер (для `Program.cs` это `text/plain`);
   - `Content-Disposition: attachment; filename=Program.cs` (имя без кавычек; как кодируются русские
     буквы, не снято: тестовый файл был с латинским именем, PyMax кодирует процентами);
   - `Content-Range: bytes 0-1387/1388` (с префиксом `bytes`; PyMax для файлов шлёт без него, но веб-клиент с ним).
   Ответ: статус 200, заголовки `range: 0-1387/1388` и `x-last-known-byte`, тело — тот же диапазон текстом
   (`0-1387/1388`). Судя по ним, загрузка умеет докачку, но для небольшого файла идёт одним запросом.
   Без `Content-Type` сервер отвечает 415. В адресе `clientType=6` (веб), адрес выдаёт сервер, строить его не нужно.
3. Сервер присылает уведомление `opcode 136` `{fileId}` (запрос от сервера с командой 0, ответ клиент не шлёт):
   файл обработан. Ожидание нужно завести **до** загрузки: оно приходит примерно через 0,3 с после неё. Пока
   уведомления нет, прикреплять файл нельзя (PyMax ждёт до 60 с). Веб-клиент отправляет сообщение через
   2 мс после уведомления.
4. `opcode 64` с `attaches: [{_type: "FILE", fileId}]` и `cid`, без `token` и без `text`, если подписи нет.
   В ответе вложение уже полное: `{size, _type: "FILE", name, fileId, token}`.

Перед загрузкой веб-клиент шлёт `opcode 65` `{chatId, type: "FILE"}` (индикатор «отправляет файл»), клиент этого не делает.

Скачивание: ссылку, судя по PyMax, возвращает `opcode 88` (`{fileId, chatId, messageId}` в ответ
`{url, unsafe}`). Проверено на настоящем MAX: ссылка
выдаётся, файл скачивается обычным GET, сервер отдаёт `application/octet-stream`, а имя файла
нужно брать из вложения.

## Видео

Вложение: `{_type: "VIDEO", videoId, token, duration, width, height, videoType, thumbnail, previewData}`.
Ссылка на видео запрашивается отдельно, `opcode 83`:
`{chatId, messageId, token, videoId}`. Ответ содержит ссылки по
качествам: `{"MP4_720": url, "MP4_480": url, ..., "EXTERNAL": "..."}`. Файл скачивается обычным GET.

«Кружок» (круглое видеосообщение) приходит тем же вложением `VIDEO`. Мост считает кружком вложение
с `videoType = 1`; это **предположение**, на настоящем кружке оно не проверялось (см. «Не проверено»).

## Чат и пользователь

- `opcode 48`: `{chatIds: [<число>]}`, ответ `{chats: [{id, type, title, ...}]}`.
  `type`: `DIALOG`, `CHAT` или `CHANNEL`. Для неизвестного чата `chats` пуст.
- `opcode 32`: `{contactIds: [<число>]}`, ответ `{contacts: [{id, names: [{name, firstName, lastName,
  type}], ...}]}`.

## Стикеры, превью ссылок и контакты

Приходят вложениями `STICKER` (`url`, `lottieUrl`), `SHARE` (`url`, `title`, `description`) и
`CONTACT` (`name`, `phone`, `vcfBody`). Стикеры и превью ссылок клиент не разбирает: в `MaxAttachment` у них заполнен
только `Type`. Контакт разбирается (`name` в `FileName`, `Phone`, `VcfBody`) и пересылается в Telegram контактом.

Формат контакта **не снят с живого трафика**: поля `name`, `phone`, `vcfBody` взяты из описаний. Поэтому `phone`
читается и строкой, и числом, а если телефона в полях нет, он берётся из визитки (строка `TEL`). Чтобы проверить формат,
отправьте себе контакт и запишите его скриптом `tools/max-traffic-recorder.js`.
`{_type: "STICKER", url, lottieUrl, stickerId, setId, width, height, ...}`.
